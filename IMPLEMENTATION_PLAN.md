# Joseph Caldwell Personal Academic Website — Staged Implementation Plan

This plan is the working roadmap from initial scaffolding through GitHub Pages deployment and VPS-portability planning. Each stage lists a goal, the files most likely to be touched, acceptance criteria, and risks or notes. Stages are intended to be small enough to review in one sitting.

The plan defers decisions called out in `PROJECT_REVIEW.md` §7 and §8. Where a decision would block progress, the stage flags it explicitly.

## Stage 1 — Astro Initialization

**Goal.** Initialize Astro inside the existing repo without overwriting planning files or replacing `.gitignore`.

**Files likely touched.**
- `package.json`, `package-lock.json` (new)
- `astro.config.mjs` (new)
- `tsconfig.json` (new)
- `src/env.d.ts` (new)
- `src/pages/index.astro` (placeholder generated by Astro; will be replaced in Stage 4)
- `.gitignore` (verify Astro's additions like `.astro/` are present; do not let `astro create` clobber existing entries)

**Acceptance criteria.**
- `npm install` succeeds.
- `npm run dev`, `npm run build`, `npm run preview` all run cleanly.
- `astro.config.mjs` sets `output: "static"` explicitly and configures `site` (and `base`, if needed) according to the deployment-target answer from `PROJECT_REVIEW.md` §7.
- TypeScript is enabled in strict mode.
- `.gitignore` has not regressed; `LICENSE` and the four planning docs are unchanged.

**Risks or notes.**
- **Blocking decision needed:** deployment target (custom domain vs. user repo vs. project repo) so `site` and `base` are set correctly from the start.
- Use `npx create-astro@latest` with the "minimal" or "empty" template to avoid pulling in opinions we'll only have to undo.
- Do not commit `node_modules/`, `dist/`, or `.astro/`.

## Stage 2 — Base Layout and Global Styling

**Goal.** Establish a single shared page layout, a header with primary navigation, a footer, a small CSS reset, and a documented set of CSS custom properties for color, type scale, and spacing.

**Files likely touched.**
- `src/layouts/BaseLayout.astro` (new)
- `src/components/SiteHeader.astro` (new)
- `src/components/SiteFooter.astro` (new)
- `src/components/SkipLink.astro` (new)
- `src/styles/global.css` (new)
- `src/styles/tokens.css` (new — color, spacing, type scale custom properties)
- `src/data/navigation.ts` (new — primary nav items)
- `src/data/site.ts` (new — site name, description, default OG image, social URLs)

**Acceptance criteria.**
- Every future page wraps in `BaseLayout`.
- The layout sets `<html lang>`, page `<title>`, meta description, canonical URL, default Open Graph metadata, and viewport.
- Navigation items come from `src/data/navigation.ts`, not hardcoded markup.
- Header is keyboard-navigable; skip-link works.
- Light-mode styling only; dark mode deferred.
- Visual feel is calm and academic; no animation libraries; no UI framework.

**Risks or notes.**
- **Blocking decision needed:** whether About lives in main nav or footer (`PROJECT_REVIEW.md` §3.1).
- **Blocking decision needed:** CSS approach. Recommendation in `PROJECT_REVIEW.md` is vanilla CSS with custom properties.
- The header must not depend on JavaScript to render its links; mobile menu (if added) should be a `<details>`-driven progressive enhancement.

## Stage 3 — Content Model Implementation

**Goal.** Translate `CONTENT_MODEL.md` into Astro content collections with `zod` schemas, plus the small data files needed for navigation and site config.

**Files likely touched.**
- `src/content.config.ts` (new — collection definitions and zod schemas)
- `src/content/research-themes/` (new collection dir)
- `src/content/projects/` (new collection dir)
- `src/content/agentic-systems/` (new collection dir)
- `src/content/dashboards/` (new collection dir)
- `src/content/writing/` (new collection dir)
- `src/content/teaching/` (new collection dir)
- `src/data/cv.ts` (new — CV asset metadata)
- `src/data/links.ts` (new — external links)
- `src/data/homepageFeatures.ts` (new — homepage feature config)

**Acceptance criteria.**
- Every collection schema enforces required fields (`title`, `slug`, `summary`) and validates the recommended status / visibility / category vocabularies via zod enums.
- `npm run build` passes content schema validation with zero entries committed (collections may be empty, but the schemas exist).
- Status / visibility vocabularies are consolidated per content type to avoid the overlap noted in `PROJECT_REVIEW.md` §3.
- A short comment at the top of `src/content.config.ts` points readers to `CONTENT_MODEL.md`.

**Risks or notes.**
- **Blocking decision needed:** content collections vs. typed data files (`PROJECT_REVIEW.md` §4.1).
- Schema changes require `astro sync` to refresh generated types; document this in the README local-dev section in Stage 9 (or earlier if it bites first).
- Keep the schemas faithful to the content model — don't quietly drop fields.

## Stage 9 — SEO, Accessibility, and Performance Pass

**Goal.** Address the items from `DESIGN_BRIEF.md` §13–15 and `AGENTS.md` §15–17 across the site.

**Files likely touched.**
- `astro.config.mjs` (add `@astrojs/sitemap`)
- `public/robots.txt` (new)
- `public/og-default.png` (new — generic site OG image)
- `public/favicon.svg` (new)
- `src/layouts/BaseLayout.astro` (canonical URL, OG, Twitter card metadata)
- Per-page metadata refinement across `src/pages/`

**Acceptance criteria.**
- Sitemap is generated at build time.
- `robots.txt` allows indexing of public pages.
- Every major page has a canonical URL, page-specific title, description, and OG image (default or per-page).
- Lighthouse run on the built output scores ≥ 95 for Performance, Accessibility, Best Practices, and SEO on the home page.
- Heading hierarchy is correct on every page (single `<h1>`, no skipped levels).
- Color contrast meets WCAG AA against the chosen palette.

**Risks or notes.**
- Performance regressions usually come from later additions (fonts, images, scripts). Establish the budget here so future PRs notice when they break it.
- No analytics added in this stage or any other.

**Files likely touched.**

**Acceptance criteria.**

- Permissions in the workflow are scoped to `contents: read`, `pages: write`, `id-token: write`.

**Risks or notes.**
- **Blocking decision needed:** deployment target if not already locked from Stage 1.
- Test the production build locally with `npm run preview` before merging the workflow.
- Do not enable the workflow until Stage 6 content has had a privacy review.

## Stage 11 — Custom Domain and VPS Portability Planning

**Goal.** Move the site to `josephcaldwell.com` (if desired) and document the path to a future VPS host without committing to it.

**Files likely touched.**
- `public/CNAME` (new — only if custom domain is used)
- `astro.config.mjs` (update `site` to the custom domain; remove `base` if root-deployed)
- `README.md` (deployment and portability notes)
- A new `DEPLOYMENT.md` (optional — captures DNS records, GitHub Pages settings, and VPS migration steps)

**Acceptance criteria.**
- DNS A/AAAA or CNAME records for `josephcaldwell.com` resolve to GitHub Pages.
- `CNAME` file in `public/` matches the custom domain.
- HTTPS is enabled in GitHub Pages settings.
- Internal links continue to resolve under the new base.
- Documentation captures: what to change in `astro.config.mjs` to host on a VPS (Caddy or Nginx serving `dist/`), how the GitHub Actions workflow could publish a tarball to a VPS instead of Pages, and which features (server endpoints, on-demand rendering) would break portability.

**Risks or notes.**
- The base-path swap is the most likely place for broken links to appear post-migration. A quick crawler check (e.g. `lychee` or Astro's `astro check`) catches most of these.
- VPS migration itself is *out of scope* for v1; this stage just makes sure we haven't designed ourselves into a corner.
- Subdomains for hosted dashboards or demos remain a separate, post-v1 effort.

## Cross-Stage Notes

- **Decision dependencies.** Stages 1–3 each have at least one blocking decision listed in `PROJECT_REVIEW.md` §7. Resolving deployment target, content-authoring approach, MDX/CSS choices, and About-in-nav unblocks the entire path through Stage 9.
- **Content review checkpoints.** Stages 6, 7, and 10 each require explicit content review by Joseph before progressing. The content-integrity rules in `AGENTS.md` §6 and the privacy rules in §7 take precedence over any schedule pressure.
- **Dependency budget.** Plan-of-record dependencies through Stage 9 are: Astro, `@astrojs/mdx` (if MDX enabled), `@astrojs/sitemap`, TypeScript, and `zod` (provided by Astro). Anything beyond that warrants a written justification before adding.
